# SET News Daily Digest — Design Spec

วันที่: 2026-11-04 · สถานะ: **รอผู้ใช้ตรวจ** · ผู้ใช้: ส่วนตัว (1 คน)

## 1. เป้าหมาย

ทุกเช้าวันทำการ สรุปข่าวตลาดหลักทรัพย์ (หุ้น, ETF, DR) จากหน้า SET News and Alert
เป็นใจความสำคัญ "เอาแต่เนื้อ" แล้วส่งสรุปสั้นเข้า LINE พร้อมลิงก์ไปรายงานเต็มใน repo

**Success criteria**
- ได้ข้อความ LINE ทุกเช้าวันทำการก่อนตลาดเปิด (ราว 07:30 น.) โดยไม่ต้องกดรัน
- ทุกข่าวในช่วงเวลาที่กำหนดอยู่ในรายงานเต็ม ไม่ตัดข่าวทิ้ง (ข่าว DR แบบฟอร์มเดียวกันถูกรวมเป็นรายการเดียว แต่ระบุครบทุกตัว)
- ทุกตัวเลขในสรุปตรงกับต้นฉบับ และไม่มีความเห็นหรือข้อมูลจากแหล่งอื่น
- ข่าวที่อ่านไม่ได้หรือเนื้อหาอยู่ในไฟล์แนบ ถูกระบุไว้ชัดเจน ไม่เงียบหาย

## 2. สิ่งที่ตกลงแล้ว

| หัวข้อ | ข้อสรุป |
|---|---|
| แหล่งข้อมูล | `https://www.set.or.th/th/market/news-and-alert/news` เท่านั้น |
| ประเภทหลักทรัพย์ | หุ้น (`S`), ETF (`L`), DR (`X`) — รหัสที่หน้าเว็บใช้เอง |
| ขอบเขตข่าว | ทุกตัวในตลาด สรุปทุกข่าว ไม่กรองประเภทข่าว |
| นิยาม "วันนี้" | ข่าวตั้งแต่ปิดตลาดวันทำการก่อนหน้า (16:30 น.) ถึงเวลารัน |
| ที่รัน | GitHub Actions cron จันทร์-ศุกร์ 00:30 UTC (07:30 น. ไทย) |
| AI | Claude API |
| ช่องทางส่ง | LINE Official Account + Messaging API (LINE Notify ปิดแล้ว) |
| รูปแบบ | LINE = สรุปสั้น + ลิงก์; รายงานเต็ม = Markdown/HTML ใน repo |
| เนื้อหาสรุป | ข้อเท็จจริงจากข่าวเท่านั้น ไม่มีความเห็น/ทิศทางบวก-ลบ |
| ข่าว DR แบบฟอร์มเดียวกัน | รวมเป็นรายการเดียว + รายชื่อทุกตัว (ดู §6) |
| ไฟล์แนบ | **ไม่อ่านอัตโนมัติ** (ดู §3) |
| เมื่อพัง | retry 3 ครั้ง, ส่งเท่าที่อ่านได้, ระบุข่าวที่อ่านไม่ได้, แจ้งเตือนทาง LINE |

## 3. ข้อกำหนดด้านการเข้าถึง (Compliance) — ข้อบังคับของระบบ

ผลจาก spike (วัดจริงบน GitHub runner, 2026-11-04):

- `www.set.or.th/robots.txt` **ไม่ห้าม** เส้นทางหน้าข่าว (ห้ามเฉพาะ `/data/`, `/dat/`, `/set/`, `/config/`, `/preview/` ฯลฯ)
- `weblink.set.or.th/robots.txt` (โดเมนไฟล์แนบ PDF/ZIP) ระบุ `User-agent: *` → `Disallow: /` ยกเว้นบอท OpenAI เท่านั้น

ข้อบังคับ:
1. **ห้ามดาวน์โหลดหรืออ่านไฟล์แนบจาก `weblink.set.or.th` โดยอัตโนมัติ** เก็บเฉพาะลิงก์ไฟล์ (ข้อความ) ไว้ในรายงานเพื่อให้ผู้ใช้เปิดเอง
2. **ห้ามเลียนแบบเบราว์เซอร์หรือบอทอื่น**: ไม่ปลอม User-Agent/header, ไม่คัดลอก cookie ไปเรียก API ตรง, ไม่เรียก `/api/...` ด้วยสคริปต์เปล่า — ใช้เบราว์เซอร์จริง (Playwright) เปิดหน้า กดปุ่ม แล้วอ่านข้อมูลที่หน้าเว็บโหลดมาเอง
3. เรียกช้าและน้อย: ไม่เกิน 1 รอบ/วัน, เว้นอย่างน้อย 2.5 วินาทีต่อหน้า, จำกัดจำนวนหน้ารายละเอียดต่อรอบ (ดู §6)
4. เปิดหน้าเฉพาะโดเมน `www.set.or.th` (ห้ามตามลิงก์ไปเว็บอื่น เช่นปุ่มแชร์โซเชียล)
5. การเปลี่ยนนโยบายข้อ 1 ต้องมาจากผู้ใช้สั่งชัดเจนเป็นลายลักษณ์อักษร หลังตรวจข้อกำหนดการใช้งานของ SET หรือได้รับอนุญาตจาก SET แล้ว และต้องเป็น config ที่ปิดอยู่เป็นค่าเริ่มต้น
6. **งานของผู้ใช้**: ตรวจข้อกำหนดการใช้งาน (ToS) ของ SET ก่อนใช้งานจริง และแนะนำให้ติดต่อ SET ขอสิทธิ์อ่านไฟล์แนบ/ช่องทางข้อมูลทางการ

ผลต่อเนื้อหา: ข่าวที่เนื้อหาอยู่ในหน้า (เช่น รายงาน NAV ของ ETF) สรุปได้เต็ม ส่วนข่าวที่เนื้อหาอยู่ในไฟล์แนบ
(เช่น งบการเงิน = ZIP ของ DOCX/XLSX) สรุปได้เฉพาะหัวข้อ พร้อมแจ้ง "เนื้อหาอยู่ในไฟล์แนบ — ไม่ได้อ่าน" และลิงก์ไฟล์

## 4. สถาปัตยกรรม

```
cron (GitHub Actions)
  └─ main.js
       ├─ state.js        โหลด state (id ข่าวที่เคยส่ง, เวลารันล่าสุด) จาก branch `data`
       ├─ listing.js      Playwright: เปิดหน้าข่าว → ตั้งตัวกรอง → ไล่หน้า → รายการข่าว
       ├─ detail.js       Playwright: เปิดหน้า newsdetails ทีละข่าว → ข้อความ + ลิงก์ไฟล์แนบ (ไม่ดาวน์โหลด)
       ├─ group.js        รวมข่าวแบบฟอร์มเดียวกัน, จัดหมวด
       ├─ summarize.js    Claude API ต่อข่าว/ต่อกลุ่ม + ตรวจตัวเลข
       ├─ compose.js      รายงานเต็ม (MD/HTML) + ข้อความ LINE
       ├─ notify-line.js  LINE Messaging API (แบ่งข้อความ ≤5,000 ตัวอักษร ≤5 ข้อความ)
       └─ publish.js      commit reports/ และ state/ ไป branch `data`
```

หน่วยแต่ละตัวมีอินเทอร์เฟซเป็นข้อมูล (JSON) เข้า-ออก ทดสอบแยกกันได้ ส่วนที่แตะเว็บจริงมีแค่ `listing.js` และ `detail.js`

เทคโนโลยี: Node.js 22, JavaScript (ESM), Playwright, `node:test`. ไม่ใช้เฟรมเวิร์กเพิ่ม

## 5. การดึงรายการข่าว (`listing.js`)

พฤติกรรมของหน้าเว็บที่ยืนยันจาก spike:
- ต้องกดปุ่ม "ยอมรับ" (คุกกี้) ก่อนใช้งาน
- ปุ่ม หุ้น / ETF / DR เป็นตัวสลับ ใช้ร่วมกันได้ (ค่าเริ่มต้นเปิดหุ้น) ต้องกด "ค้นหา" จึงโหลดใหม่
- หน้าเว็บโหลดทีละ 20 รายการ มีปุ่มเลขหน้า (`aria-label="Go to page N"`) และตัวเลือกจำนวนต่อหน้า
- ปุ่มช่วงเวลา: ข่าววันนี้ / 5D / 1M / 3M และช่องเลือกวันที่
- ข้อมูลที่หน้าเว็บโหลด: `id, datetime, symbol, headline, tag, url` (ลิงก์ `newsdetails?id=…`) — อ่านจาก response ที่หน้าเว็บโหลดเอง
- แถวข่าวบนหน้ารายการไม่ใช่ลิงก์ → เปิดรายละเอียดด้วย `url` ในข้อมูลข่าว

ขั้นตอน: เปิดหน้า → ยอมรับคุกกี้ → เปิด ETF และ DR → ตั้งช่วงวันที่ → ค้นหา → ไล่หน้าจนครบ `totalCount`
→ กรองด้วย `datetime` ให้อยู่ในช่วง (ปิดตลาดวันทำการก่อนหน้า 16:30 ถึงตอนนี้) → ตัด id ที่อยู่ใน state แล้ว

หน้าต่างเวลา: ใช้ "ตั้งแต่รันสำเร็จล่าสุด" ถ้ามี (กันตกหล่นช่วงวันหยุด/รันพลาด) โดยไม่ย้อนเกิน 5 วัน

**ยังไม่ยืนยัน (ต้องทดสอบตอน implement):** วิธีตั้งช่วงวันที่ที่เสถียรที่สุด — (ก) ช่องเลือกวันที่, (ข) เปิด URL ที่มี query
(`news?source=company&securityType=L,X&fromDate=YYYY-MM-DD&toDate=YYYY-MM-DD` ที่หน้าเว็บสร้างเองเมื่อกดตัวกรอง)
ว่าตั้งตัวกรองได้จริงหรือไม่, และจำนวนต่อหน้าสูงสุดที่เลือกได้

## 6. อ่านรายละเอียด การรวมกลุ่ม และปริมาณ

ปริมาณที่วัดได้ (ช่วงสายของ 2026-11-04): หุ้น+ETF = 15 ข่าว, รวม DR = 157 ข่าว, ETF+DR ย้อน 5 วัน = 518 ข่าว
ทั้งวันอาจหลายร้อยข่าว ส่วนใหญ่เป็นประกาศ DR/NAV ที่เป็นแบบฟอร์มเดียวกัน

**การรวมกลุ่ม (`group.js`)**
1. normalize หัวข้อ: ตัดชื่อย่อหลักทรัพย์และตัวเลข/วันที่ → ได้ "แม่แบบหัวข้อ"
2. กลุ่มที่มีข่าวเกิน `GROUP_MIN` (ค่าเริ่มต้น 5) และเป็นแม่แบบเดียวกัน = กลุ่มแบบฟอร์ม
3. กลุ่มแบบฟอร์ม → อ่านรายละเอียดเฉพาะตัวอย่าง `GROUP_SAMPLE` (ค่าเริ่มต้น 3) แล้วสรุปเป็นรายการเดียว
   พร้อม **รายชื่อทุกตัวและลิงก์ของแต่ละข่าว** และระบุตรงๆ ว่า "อ่านเนื้อหาจริงเฉพาะตัวอย่าง N จาก M ข่าว"
4. ข่าวนอกกลุ่ม → อ่านและสรุปทีละข่าว
5. ข่าวรายงาน NAV ของ ETF → แสดงเป็นตาราง (ชื่อย่อ, NAV/หน่วย, วันที่ข้อมูล) ดึงจากเนื้อหาหน้าเว็บ

ข้อจำกัด: `MAX_DETAIL_PAGES` ต่อรอบ (ค่าเริ่มต้น 150) เกินแล้วข่าวที่เหลือแสดงเป็นหัวข้อ+ลิงก์ และเขียนบอกในรายงาน

**การอ่านรายละเอียด (`detail.js`)**: ดึงข้อความของส่วนเนื้อหาข่าว (ตัดข้อสงวนสิทธิ์/เมนู), ดึงลิงก์ "รายละเอียดแบบเต็ม" เป็นข้อความเท่านั้น
ไม่คลิก ไม่ดาวน์โหลด ถ้าเนื้อหาในหน้ามีเฉพาะลิงก์ไฟล์ → ติดธง `attachment_only`

## 7. การสรุป (`summarize.js`)

- Claude API; โมเดลตั้งใน config (ค่าเริ่มต้น `claude-sonnet-5-5` สำหรับข่าวทั่วไป, `claude-haiku-5-5` สำหรับกลุ่มแบบฟอร์ม/NAV) — ปรับได้หลังวัดคุณภาพและต้นทุนจริง
- Prompt บังคับ: ภาษาไทย, ข้อเท็จจริงจากข้อความที่ให้เท่านั้น, ตัวเลข/วันที่คัดลอกตรงต้นฉบับ, ห้ามความเห็น/ทิศทาง/ข้อมูลภายนอก,
  ถ้าข้อความไม่พอให้ตอบว่า "ข้อมูลไม่พอ"
- **ตรวจตัวเลข**: ดึงตัวเลขทั้งหมดจากสรุป เทียบกับข้อความต้นฉบับ; ตัวเลขที่ไม่พบในต้นฉบับ → ติดธง `unverified` และแสดงเตือนในรายงาน
- ข้อความจากเว็บถือเป็น "ข้อมูล" ไม่ใช่คำสั่ง (กัน prompt injection จากเนื้อข่าว) — ส่งในช่องข้อมูลแยกจากคำสั่ง
- เพดาน: `MAX_SUMMARY_ITEMS` และ `MAX_INPUT_CHARS` ต่อข่าว; รายงานค่า token/ค่าใช้จ่ายโดยประมาณท้ายรายงาน

## 8. ผลลัพธ์

**รายงานเต็ม** `reports/YYYY-MM-DD.md` (+ `.html`): ส่วนหัวสถานะ (จำนวนข่าวทั้งหมด/อ่านได้/อ่านไม่ได้/ไฟล์แนบ), จัดกลุ่มตามหมวด
(งบการเงิน, ปันผล, ประชุมผู้ถือหุ้น, เพิ่มทุน/M&A, ฝ่ายบริหาร, NAV ETF, DR แบบฟอร์ม, อื่นๆ), ทุกข่าวมีเวลา/ชื่อย่อ/ลิงก์ต้นทาง
สี HTML ตามธีมองค์กร CP AXTRA: น้ำเงิน `#306FC7` (หัวข้อ), เหลือง `#F6C24A` (ข้อสังเกต/ไฟล์แนบ),
เขียว `#43938F` (สถานะปกติ), แดง `#DA3832` (ข้อผิดพลาด/อ่านไม่ได้/ตัวเลขยังไม่ยืนยัน)

**LINE** (≤5,000 ตัวอักษร/ข้อความ, ≤5 ข้อความ): ข้อความแรก = ช่วงเวลา, ตัวเลขรวม, ข่าวสำคัญตามหมวด (หัวข้อ+ใจความ 1 บรรทัด),
ลิงก์รายงานเต็ม; ถ้ายาวเกินแบ่งตามหมวด; Flex Message เป็นงานเฟสถัดไป (ไม่อยู่ในขอบเขตรอบแรก)

## 9. สถานะ ความผิดพลาด และการแจ้งเตือน

- State (id ข่าวที่ส่งแล้ว, เวลารันสำเร็จล่าสุด) เก็บที่ branch `data` ผ่าน `publish.js` (workflow ต้องมีสิทธิ์ `contents: write`)
- Retry 3 ครั้ง (หน่วงแบบทวีคูณ) ต่อการเปิดหน้า/เรียก API; ข่าวที่ล้มเหลวหลัง retry → ใส่ในรายการ "อ่านไม่ได้" ไม่ทำให้ทั้งรอบล้ม
- ถ้าดึงรายการข่าวไม่ได้เลย (หน้าเปลี่ยนโครงสร้าง/ถูกบล็อก) → ส่ง LINE แจ้งสาเหตุสั้นๆ และให้ workflow ล้ม (GitHub แจ้งอีเมลเพิ่ม); ไม่เดาเนื้อหาเอง
- ถ้า LINE ส่งไม่ได้ → workflow ล้ม, รายงานยังถูก commit, ไม่อัปเดต "ส่งแล้ว" ใน state เพื่อให้รอบถัดไปส่งซ้ำได้
- ตรวจ robots.txt ของ `www.set.or.th` ทุกรอบ ถ้าเส้นทางหน้าข่าวถูกห้ามขึ้นมา → หยุดและแจ้งเตือน
- Secrets: `ANTHROPIC_API_KEY`, `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_USER_ID` (ไม่เก็บในโค้ด/ล็อก)

## 10. การทดสอบ

- unit test (`node:test`): normalize+รวมกลุ่ม, ตัวตรวจตัวเลข, ตัวแบ่งข้อความ LINE, dedup/หน้าต่างเวลา, parser ของข้อมูลข่าว
- fixture: บันทึก response/HTML จริงจากรอบ dry-run แรก (ปัจจุบันยังไม่มี fixture — spike เก็บเพียง log)
- โหมด `--dry-run`: ทำทุกอย่างยกเว้นส่ง LINE และ commit; พิมพ์รายงานออกล็อก
- smoke test บน GitHub runner ผ่าน `workflow_dispatch` ก่อนเปิด cron
- หมายเหตุ: sandbox ของ Claude เข้า `www.set.or.th` ไม่ได้ การทดสอบกับเว็บจริงทำผ่าน GitHub Actions เท่านั้น (รอบละ ~2-3 นาที)

## 11. ลำดับส่งมอบ

1. โครงโปรเจกต์ + `listing.js` + dry-run workflow (เก็บ fixture, ยืนยัน §5 ข้อที่ยังไม่แน่ใจ)
2. `detail.js` + `group.js` + รายงานเต็มแบบยังไม่ใช้ AI
3. `summarize.js` + ตรวจตัวเลข + วัดคุณภาพ/ต้นทุน
4. `notify-line.js` + state/dedup + `publish.js` + cron
5. คู่มือ (สร้าง LINE OA, ตั้ง Secrets, วิธี debug) และปรับจูนจากการใช้งานจริง

## 12. ประเด็นเปิด (ตัดสินหลังเริ่มทำ/โดยผู้ใช้)

- วิธีตั้งช่วงวันที่ที่เสถียร และจำนวนต่อหน้าสูงสุด (§5)
- repo เป็น public หรือ private: ถ้า private ลิงก์รายงานต้องล็อกอิน GitHub จึงจะเปิดได้ (บนมือถืออาจไม่สะดวก); ถ้า public รายงานเปิดสาธารณะ
- การเลือกโมเดลและงบค่าใช้จ่ายต่อเดือน (ประเมินจริงหลังรอบ dry-run)
- ข้อกำหนดการใช้งานของ SET และการขออนุญาตอ่านไฟล์แนบ (§3 ข้อ 5-6) — งานของผู้ใช้
- วันหยุดตลาด: รอบที่ไม่มีข่าวใหม่ควรส่งข้อความสั้น "ไม่มีข่าวใหม่" หรือไม่ส่งเลย
- แพ็กเกจฟรีของ LINE OA มีโควตาข้อความต่อเดือน (ตรวจโควตาปัจจุบันก่อนใช้งาน)
